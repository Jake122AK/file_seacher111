# 日和見 — 太陽プロトタイプ

伏見稲荷・千本鳥居を舞台にした「時刻パズル」の第一プロトタイプ。
`hiyorimi.html` をブラウザで開くだけで動く（WebGL2 必須、外部依存ゼロ）。

## このプロトタイプが証明しようとしていること

企画全体の生死を分ける問いは一つだけ:

> **ダイヤルを回して影が動くのは、それ自体が気持ちいいか？**

ここが No ならパズルもナラティブも意味がない。

第一版は太陽の挙動と手触りだけだった。第二版でキョンシーを入れ、
**その太陽が武器になる**ところまで通した（下の「キョンシー」節）。

## 中核の設計判断 — 太陽を「2本のスライダー」から「暦」に変えた

元の描画エンジンは太陽高度と方位が独立した自由スライダーだった。それでは
パズルにならない。自由度が高すぎて総当たりで解けてしまうからだ。

かわりにプレイヤーが握るダイヤルは2つだけ:

| ダイヤル | 範囲 | 意味 |
|---|---|---|
| **節気** | 二十四節気 24段 | 太陽が描く弧の**形**が変わる |
| **時刻** | 0:00–24:00 連続 | その弧の上のどこにいるか |

高度と方位はこの2つと**緯度 34.9671°N から天文計算で一意に決まる**
(`c2_astro.js` 節)。結果として:

- **到達できない太陽位置が生まれる。** 京都で「真北から低く差す光」は
  一年のどの瞬間にも作れない。これが物理的な壁になり、パズルが成立する。
- **夏至と冬至が極点になる。** 影が最も短い日と最も長い日がゲームの
  「最強の道具」として暦の両端にあり、そこへ至る動機になる。
- **午前と午後で同じ高度が2回来る。** 方位は鏡像、光の色も違う。
  「高度は合っているのに解けない」という良質な引っかかりが自然発生する。

### 実装した天文

二十四節気は黄経15°ごとに正確に並ぶので、節気の番号だけから赤緯が閉じた式で
出る（暦テーブル不要）。均時差と経度差（明石135°Eとの0.77°）も入れてある。

検証値（`node astro_test.js` 相当）:

| | 日の出 | 南中 | 日の入 | 南中高度 |
|---|---|---|---|---|
| 春分 | 06:01 | 12:05 | 18:09 | 55.03° |
| 夏至 | 04:43 | 11:58 | 19:13 | 78.47° |
| 秋分 | 05:46 | 11:50 | 17:54 | 55.03° |
| 冬至 | 07:01 | 16:49 | 16:49 | 31.59° |

実際の京都の暦とのずれは**1〜3分**。南中高度は理論値
(90° − 緯度 ± 23.44°) と小数点以下まで一致する。均時差が効いているので
春分の南中は 12:05、秋分は 11:50 と正しく非対称になる。

### 参道の方位

世界座標 +Z（参道が登る方向）の方位を **75°（ENE）** に設定した。
実際の千本鳥居が東北東に登るのに合わせてあるが、同時にゲーム上の判断でもある:

- 春分・秋分の日の出（方位 89.6°）は**参道をまっすぐ射抜く**
- 夏至は 60.5°、冬至は 118.5°

つまり**一年をかけて日の出が参道の軸を横切る**。これがそのままパズルの
主軸になる。

## 手触りのための実装

- **ダイヤルは目標値。太陽は臨界減衰でそれを追う。** フレームレート非依存
  (`dampWrap`)。時刻は λ=5.5、節気は λ=3.2 と重くしてある（暦が動くのは
  儀式的であってほしい）。真夜中をまたぐときは短い方向に回る。
- **IBL は毎フレーム焼かない。** 太陽の直射（＝影と鏡面）は毎フレーム
  更新するが、環境光キューブは角度が 0.32° 動いたときだけ、しかも
  掃引中は2フレームに1回に間引く。目が追うのは影であって環境光ではない。
- **TAA は太陽が動いている間だけ履歴を捨てる** (`0.88 → 0.54`)。
  動く影に対する TAA ゴーストはパズルゲームでは致命傷になる。
- `T` で早送り（一日 ≈ 28 秒）。`Q`/`E` で時刻、`Z`/`X` で節気。

## グラフィック側で書き直した部分

太陽が一日中どこにでも行けるようになった以上、夕暮れ専用に手で調整された
ライティングは通用しない。物理から出るように書き直した。

- **太陽の色は美術指定ではなく大気の透過率**。天頂での Rayleigh + Mie
  光学的厚さに相対エアマス（Kasten-Young）を掛けて指数を取る。この一本の式
  だけで、南中は暖かい白 (9.9, 9.3, 8.0)、地平線際は深い赤 (1.1, 0.31, 0.01)
  になる。手描きのグラデーションは一切ない。
- **自動露出は実測**。ここは一度作り直した。最初は太陽高度から露出を
  推定していたが、**屋根のある回廊の中では太陽が高いほど目に届く光は
  減る**（笠木が遮る）。開ループ推定は、暗くなった瞬間に絞りを絞る。
  実際に南中の絵が真っ黒になった。
  かわりに描画済みフレームを測る:中央重点の平均輝度を 1×1 のターゲットで
  適応させる（Reinhard 平均。log 平均はこのシーンの真っ黒な領域に
  引きずられて昼夜の差が 1.5 倍しか出なかった）。**読み戻しもストールも
  ない**。明順応は速く (τ≈0.7s)、暗順応は遅く (τ≈1.8s)。
  **完全な正規化はしていない**——`pow(L, -0.75)` にして、夜は夜として
  暁の約 70% の明るさに見えるようにしてある。真夜中と真昼が同じ明るさに
  なるのが自動露出の典型的な失敗なので。
  スライダーは絶対値ではなく**補正**に変えた。ブルームの閾値も露出に
  追従させてある（さもないと南中で画面全体が滲む）。
- **夜**。地平線下でも破綻しないよう、大気光の底と**京都の街明かり**
  （方位300°の地平線、雲の底を舐める）を空シェーダに追加。
- **星**。天球に固定した3オクターブの星野を、天の北極まわりに時角ぶん
  回している。つまり夜のあいだ星は正しく東から昇る。キューブマップに焼くと
  エイリアスするので、空ピクセルに解析的に描いている。
- **石灯籠**は太陽が沈むにつれ点る（点光源と自己発光の両方）。

## キョンシー — 追跡と戦闘

### なぜキョンシーなのか（技術的な理由）

このエンジンにスケルタルアニメーションは無い。人型を歩かせるのは本来苦手。
しかし**キョンシーは硬直したまま跳ねる**のが定義的な動き — 死後硬直で膝も肘も
曲がらないから、両腕を前に突き出したまま跳んで移動する。つまり
**剛体のまま animate できる**。弱点が仕様になる、数少ない題材。

実装は4つの剛体パーツを手組みの階層に乗せただけ:

| パーツ | 三角形 | 動き |
|---|---|---|
| 体（官服・帯・朝靴） | 960 | 跳躍アーク + 着地スカッシュ |
| 頭（頭蓋・辮髪・官帽） | 1188 | 体に遅れて追従（バネ）+ ゆっくり首を振る |
| 両腕（袖・拳） | 544 | 体にさらに遅れて追従 |
| 符 | 40 | 跳躍の上下加速度で駆動される振り子 |

跳躍サイクルは 沈み込み → 跳躍 → 滞空 → 着地 → 整い の5段階で、
**前進は滞空中にしか起きない**。これが「跳んでいる」ように見えるか
「滑っている」ように見えるかの分かれ目。

### 戦闘 = 暦

キョンシーは**直射日光で焼ける**。つまり武器は節気と時刻のダイヤルそのもの。
ある一体を祓うには「今その位置に光が届く時刻はいつか」を暦から割り出す。

日光判定は、影マップを読み戻せないので鳥居列の解析モデルに対して太陽光線を
マーチする。参道の z 座標がそのままパラメータで、接線が +Z から18°以上
外れないので、最近点を解かずにローカル座標が取れる。梁の占有は5cm刻みの
ルックアップに焼いてあるので1サンプル数命令。

実測した「光が届く場所」（横方向オフセット別、`.` は日陰）:

```
             lateral:  -1.0   0.0   1.0
春分  7:00  el 11.3    0.74    .     .
春分 12:00  el 55.0    0.85   0.99  0.90
夏至 17:00  el 24.6     .      .    0.90
秋分  6:00  el  2.1     .     0.28   .
冬至  9:00  el 18.3    0.85   0.83  0.73
冬至 12:00  el 31.6    0.85   0.99   .
```

季節と時刻の組み合わせごとに**答えが違う**。南中は回廊の中央まで光が落ちる
（高い太陽は梁の隙間を抜ける）が、冬至の低い太陽は片側にしか届かない。
夜はどこにも届かないので、夜は戦えない — 逃げるしかない。

キョンシーは |横方向| < 1.55 の範囲、つまり柱の内側に留まるので、
上の表の3列が実際に意味を持つ列になる。

### その他

- 接触すると**呪い**が溜まる。溜まるほど画面から彩度が抜け、赤に寄り、
  周辺が落ちる。満ちると参道を16m引き戻される。
- **Space で鈴**。半径6.2mのキョンシーを1.3〜2.7秒硬直させ、突き飛ばす。
  クールダウン3.4秒。追い詰められたときの逃げ道。
- 焼けている個体は炭化し、遅れて熾火が灯る（発光は burn > 0.15 から立ち上がる）。
  周囲を照らす点光源も持つので、燃えている間だけ回廊が明るくなる。
- **R** で再配置。

新マテリアル3層を手続き生成で追加（官服の綾織り＋団花、屍蝋の肌＋屍斑、
符の紙繊維＋辰砂の呪文）。鳥居と同じベイク経路なので質感の解像度は同じ。

## 境内 — 拡張のための土台

伏見稲荷全体へ広げるための第一歩として、**楼門から本殿までの境内**を作った。
千本鳥居とは別エリアとして作ってあり、後で繋げられる構造にしてある。

### エリア構造（統合のための設計）

```js
WORLD.add({ name:'keidai', contains:(x,z)=> z < 1.0, ground:(x,z)=>({...}) });
WORLD.add({ name:'senbon', contains:()=> true,       ground:(x,z)=>({...}) });
```

エリアは**自分の地面・当たり判定・描画リスト**を持つ。カメラは `WORLD` に
訊き、`WORLD` はプレイヤーが立っているエリアに訊く。**三つ目のエリア
（お塚群、四ツ辻、一ノ峰…）を足すときは、この2行に1行足して地面関数を
書くだけ**で、カメラにも描画にも手を入れなくていい。

当たり判定は AABB のリスト（`WORLD.boxes`、現在44個）。柱・建物・狐像・
灯籠が入っている。

境内は自分の中心線で作ってあり、`KX = 3.02`（参道の入口の x 座標）で
世界座標へずらしている。これで**境内の床と参道の床が段差なく繋がる**。
参道側の散乱物（杉・下草・落葉・地面ストリップ）は `t = -16` から始まって
いて本殿を突き抜けていたので、`CORRIDOR_T0 = 1.0` で切った。

### 建てたもの

実際の配置に沿って、西から東へ登る:

一之鳥居 → 二之鳥居 → 手水舎 → **楼門**（1589年、秀吉寄進）→ **外拝殿**
→ **本殿**（五間社流造）→ 参道へ。段丘で -4.3m から +0.2m まで登る。

### 日本建築のための道具

- **`roofShell()`** — 屋根。平面上の高さは軒からの正規化内挿で決まり、
  **x と z の内挿の `min` を取ると 45° の隅棟が自動的に出る**。1未満の
  指数を掛けると**照り**（凹みの反り）になる。**反り**（軒が隅で跳ね上がる）
  は軒側に加えて棟に向けて減衰させる。この2本の曲線だけで
  「重く見えて隅が飛ぶ」という日本の屋根の性格が出る。
  軒の前後で深さを変えられるので、**流造の非対称な長い前流れがそのまま作れる**。
- **`bracketSet()`** — 斗栱（大斗・肘木・巻斗3・尾垂木）。
  軒下の組物は、建物が「日本建築に見えるか」を決める単一で最大の要素。
- **`rafterRow()`** — 垂木。**`railing()`** — 高欄＋擬宝珠。
- **`buildTamagaki()`** — 玉垣。

マテリアル2層追加: **檜皮葺**（46段の葺き重ね、段ごとの木口の線と影）、
**銅**（窪みに緑青、高い所に金気）。

### 本殿を伏見稲荷らしくする

一般的な流造と伏見稲荷の本殿（1494年、重文）を分けているのは、
主に次の3つ。全部入れた。

- **向拝 + 唐破風** — 前へ張り出した拝所と、その上に載る曲線の破風。
  唐破風の輪郭は「隅から凹んで立ち上がり、中央で凸に反る」S字で、
  **`cos³` がちょうどその変曲を持っている**。両端に少し持ち上げを足すと
  兎毛通の跳ね上がりになる。`karahafu()` はこれ一本。
- **蟇股** — 梁の間に並ぶ carved strut。輪郭だけが遠目に残るので、
  切り抜きではなく天板＋開いた二本足＋金具の塊で組んだ。
- **金具** — 柱の上下の金輪、扉の八双金具、懸魚、千木・鰹木。
  伏見稲荷は「朱と白と金」で出来ている。

あわせて **内拝殿**（鈴緒3本と賽銭箱つき）、**絵馬掛け**、境内の樹木を追加。

### この境内の現状（正直に）

- **楼門・外拝殿・内拝殿・本殿と表参道は見られる状態**。
- **俯瞰にすると世界の縁が見える。** 境内の地面は外へ落として山肌に
  したが、まだ多角形の縁で終わっている。参道側の森と境内の森も
  視覚的に繋がっていない（間に隙間がある）。地上を歩く分には見えない。
- **白壁が暗い**。軒の深い影に入るので空の青い環境光しか当たらず
  青灰色に見える。実際の白壁はもっと明るく浮く。反射光の追加が要る。
- 奥宮、社務所、権殿、神楽殿はまだ無い。
- 千本鳥居の先（奥社奉拝所、熊鷹社、四ツ辻、一ノ峰）はまだ無い。

## 狐巫女 — キャラクターモデル

### 最初は狙いを丸ごと外していた

一度作り直している。初回はマズルがあり、全身が毛で覆われ、指行性の脚と
肉球を持つ「狐」を作った。それは**ケモノ**であって、参照として挙げられた
**ウマ娘ではない**。

**ウマ娘は獣人ではない。動物の耳と尻尾を持った人間の女の子である。**
それ以外は全部人間で、魅力はほぼ顔と髪に宿っている。ジャンルごと
間違えていた。

作り直した前提:

- **人間の体、人間の肌、蹠行性（普通の脚）。毛は耳と尻尾だけ。**
- **マズルなし。** アニメ顔 —— 頭蓋が大きく顔が小さい、頬骨は広く、
  顎は小さく尖った顎へ一気に絞る。
- **目は巨大で、顔の面にほぼ平ら**に貼る。眼球を眼窩に沈めない。
  **上まつ毛が、この model 全体で最も強いアニメ信号**。
- **髪はテクスチャではなくシルエット** —— キャップ、前髪、顔を挟む横髪、
  長い後ろ髪、アホ毛。
- 6.7頭身。
- **巫女装束**（白衣・緋袴）。この社に属し、狐耳と並べたとき日本人の目に
  即座に読め、そして**広い袖と長い裾が、スキニングの無いキャラクターが
  綺麗に曲げられない関節をちょうど隠してくれる**。

### 決定的だったのはトゥーンシェーディング

ジオメトリ以上に効いた。**PBRのままではアニメ顔はプラスチック人形にしかならない。**
頬を横切るなめらかな陰影勾配こそ、このスタイルが取り除いているものだから。

`FS_LIGHT` にマテリアル16番以上を分岐させたパスを追加した:

- 拡散をやわらかい境界で**2段に量子化**
- 影を**寒色に寄せる**（セル画がやるとおり）
- 環境光は**平坦で明るく**（陰が濁らないように）
- GGXのローブを捨て、**制御された1つのハイライト**に置換（髪は広く、肌はほぼ無し）
- **リムライト** —— 暗い回廊に沈まず輪郭が立つ

あわせてGバッファ側で、世界の風化（大スケールノイズ・汚れ・濡れ）が
キャラクターに乗らないよう16番以上を除外した。

### マテリアル4層

肌、髪、**平色**、虹彩。平色の1層に、まつ毛・眉・口・白目・耳の内側を
**tint で色分け**して載せている。これで**顔全体が3層＋1で済む**
（素直にやると11層必要だった）。

虹彩は陰影ではなく**描いてある** —— 中心が明るく、放射状の繊維、縁に
暗いリンバルリング。極座標で描いた絵なので、**放射状UVを持つ専用の
ドーム円盤**を用意した（楕円体の球面UVでは赤道方向に伸びてしまう）。

### 途中で潰したバグ

- **目が顔の面より13mm奥に埋まっていた。** 眼窩の暗い穴に見えていた。
  アニメの目は眼窩の中の球ではなく、**顔の面に載る浅い円盤の重ね**。
- **虹彩がずっと見えなかった。** ドーム円盤の**巻き方向が裏返っていて
  背面カリングに丸ごと食われていた**。レンダリングを回さずに、
  頂点順序から面の向きを数値で出して確定させた（-1 → +1）。
- 瞳が虹彩より前に出ていて、見えていた僅かな中心も覆っていた。

三角形数 約9,700。

### 磨き込み — 「初期ポリゴン」に見せていたもの

指摘を受けて徹底的に詰めた。**「初期ポリゴンに見える」原因は3つ**で、
どれもモデリングの丁寧さの問題ではなかった。

#### 1. 輪郭線（これが最大）

**インクラインの有無が、セル画と「テクスチャの無いポリゴン」を分ける。**
陰影をどれだけ詰めても、線が無ければポリゴンにしか見えない。

**背面法（inverted hull）**で実装した。サーフェスを複製し、各頂点を
**自分の法線方向へ押し出し**、巻き方向を反転する。背面カリングが働くと、
複製は**元の形のシルエットからはみ出した部分だけ**が見える —— それが
そのまま、形の周りを回る一定の太さの線になる。

線は**シェーディングしない**。マテリアル20番を専用に用意し、ライティング
パスで素通しの色として出力する。陰影を付けると「暗いプラスチックの縁」に
なって、描かれた線には見えない。

そして**線は黒ではなく色を持つ**。肌の周りは暗い暖色の茶、髪は暗い紫寄り、
緋袴は暗い朱。パーツごとに tint で指定している。**肌を純黒で囲むと
シールに見える。** 太さもパーツ別（顔 2.0mm 〜 袴 3.4mm）で、顔の線を
太くすると造作が潰れる。

#### 2. ポリゴン密度

頭部 24 → 44分割、頭蓋 12 → 22段、髪キャップ 22 → 40分割。
面取りが見えなくなった。三角形数 9,700 → **32,500**（輪郭シェル込み）。

#### 3. 髪のシルエット

前髪7枚の均等な葉 → **長さ・幅・傾き・奥行きが全部違う11枚 + 内側に
短い5枚の второй層**。均等に並べると櫛の歯に見える。横髪も片側3本に。
後ろ髪は本体 + 長さの違う7本の毛束で、毛先が一直線に切れないように。

### さらに潰したバグ

**ロフトのリング軸はワールドXYではなく、平行移動されたフレームに従う。**
まつ毛のパスは横方向に走るので、フレームは rx を縦、ry を奥行きに割り当てる。
値が逆で、**まつ毛が「頭蓋に突き刺さった薄い刃」になっていた**。眉も同じ。

### 根本的な間違い —— 顔は「モデリング」するものではない

参考画像を見て、**最初から根本的に外していたこと**が分かった。

**アニメ3Dキャラクターの目・まつ毛・眉・口・鼻は、ジオメトリではない。
滑らかな頭部に貼られた「絵」である。**

一つ一つをポリゴンで作っていたから、顔に部品が貼り付いて見えていた。
まつ毛を板で作れば板に見えるし、虹彩を円盤で作れば円盤に見える。
**当たり前のことだが、これに気づくまで4回作り直した。**

#### Canvas 2D で顔を描く

だから、実際に描く。`drawAnimeFace()` は Canvas 2D で顔を1枚の絵として
描き、`texSubImage3D` でマテリアル配列の専用スロットに流し込む。
Canvas はベジエ・グラデーション・クリップを持っているので、
**アニメの目に必要なものは全部揃っている。**

そして**アニメの目は「色のついた円盤」ではなく、意図のある約10層の積み重ね**:

1. **瞼の開口** —— 上瞼は高く弧を描き、頂点は中央より内側。下瞼は浅い。
   この非対称が目の性格を決める。
2. **白目** —— 目頭側は寒色、下は白。
3. **虹彩の縦グラデーション** —— 上は瞼の影で深く、下は反射光で明るい。
   **この一本のグラデーションの向きが、目がガラスに見えるか絵の具に
   見えるかを決める。**
4. 放射状の繊維、5. 下部の明るいリング、
6. **リムバルリング** —— 硬い暗い縁。これが無いと虹彩が平らに見える。
7. 瞳孔、8. **上瞼が眼球に落とす影**、
9. **キャッチライト** —— 大が上外、小が下内。
10. **上まつ毛** —— 線ではなく**インクの楔**。瞼に密着し、外側3分の1で
    太くなり、目尻を越えて跳ねる。まつ毛の棘2本つき。
11. 下まつ毛（外半分のみ）、12. 二重の線。

加えて頬の赤み（グラデーション＋アニメ的な3本線）、鼻は**影だけ**、
開いた口（口内・舌・上唇の線）。

#### 頭部は「顔の面」に貼るための1枚のサーフェス

顎から頭頂まで1枚のロフト。**正面平行投影のUV**なので、描いた絵が
歪まずに顔に乗る。耳より後ろの頂点はUVを絵の外へ押し出してクランプさせ、
無地の肌を拾わせている（どうせ髪が覆う）。

### さらに潰したバグ

**顔が真っ黒な仮面になった。** 頭部のリングが `loft()` とは逆回りに
パラメータ化されていたため**三角形の巻き方向が鏡像**になり、頭が
カリングされて**自分の輪郭シェルだけが見えていた**。
頂点順序から面の向きを数値で出して確定（-1 → +1）。

### 髪・衣装・手足

顔の次に、シルエットを作っている要素を作り直した。

#### 見落としていた重大な不整合

**衣装のマテリアルは LINEN(15) で、トゥーン境界(16)の下にあった。**
つまり**顔と髪はセル、服は物理ベースで描かれていた**。一人のキャラクターに
二つのライティングモデルが同居していた。`CLOTH`(22) を境界の上に作って移した。

#### 髪 — 分け目から生える

均等な葉が冠から垂れると「歯のついたヘルメット」に見える。実際のアニメ髪は
**分け目から生え、S字に外へ払い、額の中央を見せる**。全ての房を
Catmull-Rom の曲線（`sweptLock`）にして、直線の房をゼロにした。

#### 天使の輪

**アニメの髪はスペキュラの点を受けない。頭を一定の高さで巡る「光の帯」を受ける。**
法線からではなく**ワールド高さから**駆動しているのがポイントで、そうしないと
房ごとにハイライトが割れて輪にならない。頭の関節位置から毎フレーム更新している。

#### 袴 — 襞

**袴が袴に見えるのは襞（ひだ）があるからで、それ以外の理由はない。**
リング半径を三角波で変調し、指数で尖らせて折り目を作っている（11襞）。
最初は変調が浅すぎて、量子化された拡散の同じ段に全部落ちて見えなかったので、
深さを 0.17 → 0.32 に上げた。

#### 袖

**幅0.20mの袖を左右に付けたら、胸の前で合わさって白い一枚板になった。**
白衣の袖は横に狭く前後に深い —— 腕の脇に垂れるもので、胸を包むものではない。
横 0.121m / 奥行 0.170m に作り直し、袖口を折り返して開口部に厚みを持たせた。

#### 手足

手は4本のチューブの塊だった。アニメの手は**小さく、滑らかで、単純**
—— 関節も血管も無い。掌を薄く、指を4本×先細り＋わずかなカール、
親指を正しい角度に。足は足袋（親指の割れつき）＋草履（二層の底＋鼻緒）。

## 移動の手触り

元は 1.62m の三脚が 1.55 m/s で幅 1.15m のスロットを動いていた。
背が高く、遅く、閉じ込められて見える。変更:

| | 前 | 後 |
|---|---|---|
| 視点の高さ | 1.62m | **1.46m** |
| 歩き | 1.55 m/s | **4.20 m/s** |

### 視点

- **ホイールで拡大縮小**（画角 14°〜88°）。`-` / `=` でも。
  スナップさせず減衰させている（14°でいきなり切り替わると酔う）。
- **`F` で俯瞰モード** — カメラが体から外れ、当たり判定も重力も無くなる。
  移動は**視線方向**に走るので、下を向いて前進すれば降りる。
  覚える軸が増えないし、全体を見に上がるのがいちばん速い。
  `Space` で上昇、`Shift` で加速。

鳥居の内法は 1.86m、柱は中心 1.085m に立つので、±2.75 にすると
**柱の外側の縁石まで出られる**。そこが低い太陽の光が入ってくる場所なので、
可動域の拡大はそのまま戦術になる。

加えて速度に応じた加減速と歩調に同期したヘッドボブを入れた。

## 第14稿 — リアル方向（モンハン級）への作り直し

「モンハンのキャラクターくらいのレベルに」＝アニメ調をやめて実在感を取りに行く、という方針転換。
セル調のパスを全部外し、肌・髪・布・眼を物理ベースで組み直した。

### ライティング

| 対象 | 手法 |
|---|---|
| 肌（MAT.SKIN / MAT.FACE） | wrap diffuse（WRAP=0.38）＋ ターミネータ限定の赤い透過 `vec3(0.760,0.235,0.130)`、鏡面は2ローブ（油膜の広い方 + 表皮の狭い方、f0=0.028） |
| 髪 | Kajiya-Kay。接線をずらして `pow(sinθ,90)` の芯と `pow(sinθ,16)` の広がりの2ローブ |
| 輪郭線 | 廃止（`CFG.inkLine = false`）。実写寄りの造形に反転ハルを付けるとゴムの継ぎ目になる |

### 顔 — 「描く」から「彫る」へ

アニメ版は顔の造作をテクスチャに描いていた。リアルにすると、それは正面からしか成立しない。
かといって鼻・唇を別メッシュで載せると、**頬と接するところに必ず法線の段差ができて、
面に貼り付いたヒレに見える**。2回のレンダで同じ結論が出た。顔には継ぎ目がない。

最終形は **顔面全体を1枚の高さ場**にした。

- `headZ(x,y)` — 頭蓋シェル。断面は円ではなく**超楕円（HEAD_N = 2.45）**。顔は正面が平らで側面も平らで、
  曲がるのはこめかみ。断面を円にしたのがマネキンに見えた根本原因。
  さらに眼窩・頬骨・上顎・側頭のレリーフを持つ。
- `faceRelief(x,y)` — 鼻背・鼻翼・鼻翼溝・人中・上唇・下唇・口裂・頤唇溝・頤結節・眉弓を、
  すべてミリ単位の高さで定義したガウス／超ガウスの和。
- `mikoFacePatch()` — その高さ場を (x,y) グリッドで張り、縁でレリーフを0にフェードしてシェルに溶かす。
  UVは頭部と同じ正面平行投影なので、描いた顔がそのまま乗る。

鼻は稜線で+9.6mm、幅は中心10.2mm→x=12mmで2.9mm→x=21mmで0.6mmと落ちる。
「細い管」ではなく「広く緩い隆起」であることが、鼻を鼻に見せる。

### 眼 — 実際の球と実際の瞼

- `mikoEyeball` 半径12.2mmの球、`mikoIris` 虹彩12.8mm＋角膜の膨らみ。
- `mikoLid` — 瞼はフランジ。球の上の瞼縁から始まり、球を包み、`faceZ()` で頭蓋に着地する。
  瞼が無いと眼球はマスクに貼ったビー玉にしかならない（実際そう描画された）。
- 瞼裂は上7.2→5.8mm に詰めた。上瞼が虹彩の上端を隠さないと、驚いた顔になる。

### 顔テクスチャ

塗りの座標を全部**ワールド座標**に置き換えた（`PX/PY/PW/PH`）。
以前は塗りがキャンバス比率を直に持っていて、モデルを動かすたびに睫毛と瞼がずれた。

### 比率

眼の高さが頭高の37%しかなく、額が異常に高かった。頭頂を 0.1755 → 0.166 に詰め、
眼・眉・鼻・口を上げて43%に。人間の頭は眼が概ね中央にある。

### 髪

- ロックは**リボン**にした。断面が丸い筒だと、どう曲げても藁になる。厚み26mm→6.5mm。
- 前髪17枚。根元は分け目の一点ではなく、頭皮の楕円上のそれぞれの位置から生やす。
  一点から扇状に出すと、ハリネズミになる（一度そうなった）。
- 横髪6枚／側、後ろ髪11枚。

### 影

近景カスケードのバイアスが鳥居用だった。法線オフセット12mmは4mの柱では無だが、
**顔では鼻より大きい**。顔中に出ていた斑点は、髪の落ち影が特徴より大きく変位したもの。
カスケード0を 11m → 6m に詰め、オフセットを同率（0.6→0.32）で縮め、PCFを広げた。

### 見つかったバグ

- **袴が裏返っていた。** リングが下向きに並ぶので、頭部と同じ巻き方だと法線が内側を向く。
  正面が背面カリングで消え、背面の内側と、その手前に立つ脚が見えていた。
- **腕が袴の中に折り込まれていた。** `compose()` は R = Ry·Rx·Rz。下を向いた腕は
  `(L·sin(rotZ), -L·cos(rotZ), 0)` に写るので、右腕の roll は正で外に開く。
  rest が負だったため両手が x=±0.037 — 幅0.16の袴の内側に入り、腕が一度も見えていなかった。

### 正直に

ここまでで到達しているのは「破綻のない実在系キャラクター」であって、
モンハンの製品版キャラクターではない。あちらは ZBrush の彫刻、4Kの手描きテクスチャ、
実スキャン、専用のスキニングとリグで作られる。手続き的なJSで届かないのは主に

- スキニング（今は剛体のジョイント階層。肩・肘・膝が折れると破綻する）
- 皮膚の微細な起伏（毛穴はあるが、皺・シボ・産毛は無い）
- 白衣が箱に見える（肩が角、袖の落ち感が均一、パネルの縫い目が無い）
- 手指がまだ小さく単純
- 歩き・走り・跳びのアニメーションが未実装

## 第15稿 — アニメ顔へ。UI、髪、服のシワと風

### まず直したもの: パネルが閉じられなかった

`#panel` が画面いっぱいに出て、閉じる手段が無かった。モデルが見えないので**これが最優先**。

- タイトル行をタップ（クリック）で開閉。`▾ / ▸` ボタンも付けた
- 画面が狭いとき（幅760px未満）は**最初から閉じた状態**で起動する
- ピンチで寄り引きできるようにした（それまでホイールだけだった）

### アニメ顔

方針転換。リアル方向に積んだもののうち「構造」は残し、「比率と陰影」を全部アニメ側に振った。

| | 前（リアル） | 後（アニメ） |
|---|---|---|

#### 眼を2回作り直した

**アニメの眼は球ではない。** 37mmの開きを24mmの眼球に開けると、**内眼角が顔より14mm奥に沈む**。
頬が眼の上に閉じて、残るのは細い溝だけ。曲率半径を46mmに上げても解決しない
——**顔そのものが片目の幅で5.8mm落ちている**ので、眼の軸に中心を置いた球では追随できない。

最終形はアニメのモデルが実際にやっている構造：

- `eyeSink(x,y)` — 顔の高さ場から眼窩を掘る（中心3.6mm）
- `eyeSurfZ(x,y) = faceZ(x,y) + eyeSink(x,y) - 0.7mm` — 眼のシートは**掘った分をそのまま足し戻す**。
  つまり眼の面は定義からして常に顔と平行で、調整項がひとつも要らない
- 白目・虹彩・瞼はすべてその上の (x,y) パッチ。鼻や口と同じ1枚の高さ場の上に乗る

検算：瞼裂の内側どこでも、眼のシートは瞼面より **+0.52mm** 手前。潜り込みゼロ。

#### 顔に髪の影を落とさない

これが最後の一手だった。フラットな肌に影マップの硬い境界が乗ると、**絵の上に灰色の面が貼られたように見える**。
実際そう描画された。製品のアニメ3Dが顔に専用の影処理を持っているのはこのため。
`shF = mix(1.0, sh, 0.34)` ——気配だけ残して落とさない。

#### 虹彩

1回目は瞳孔を r<0.40 で描いて**鍵穴**になった。瞳孔が大きすぎると色を乗せる面積が無くなり、
ハイライトも瞳孔の中に落ちて消える。瞳孔を r<0.30 に絞り、虹彩を広く明るくして、
**ハイライトは色のある所に、真っ白・不透明で**置いた。柔らかいハイライトはハイライトではない。

### 髪

リアル化のときリボン17枚に細くしたら**紐**になった。アニメ髪は逆で、**少数の大きく綺麗な形**。

- 前髪 11枚、幅31〜44mm、厚み9mm、先端は w1 = w0×4% で**尖らせる**
- 長さを詰めて、中央は眉の上・両脇は頬で終わるように（前まで眼まで垂れていた）
- 横髪・後ろ髪も太く、枚数を減らした

### 服 — シワと風

**シワ。** 布のシワは形であって模様ではない。数ミリの深さが無いと稜線に沿って光を拾わない。
`wrinkleGeo()` が法線方向に、(高さ, 角度) の3波の和を **1.55乗で尖らせて** 変位させる。
サインのままだと波紋になるので、尖らせて「稜線と平面」にする。白衣6.2mm / 袖7.2mm / 袴4.6mm。

法線は面から取り直す（`recalcNormals`）。loft は継ぎ目の頂点を重複させるので、
**位置でまとめて平均しないと衣服の脇に明るい線が1本走る**。

**風。** 頂点シェーダの風は `max(aPos.y, 0.0)` ——地面から生える草木用だった。
布は関節から**下に**垂れるので、全ての衣服が完全に静止していた。
`uWind` が負なら「垂れる」＝関節から下方向の距離で揺れる、に変更。袖 -0.085 / 袴 -0.050 / 髪 -0.034。

### 残っている（正直に）

- **白衣がまだ箱。** 肩が角、袖の落ち感が均一、縫い目とパネルが無い
- **顔の輪郭がまだ広い。** 頬が張っていて顎が重い
- 髪は塊としては良くなったが、面の分割が粗く、額との境が硬い
- スキニング未実装。肩・肘・膝の段差と、歩き・走り・跳びは全部この先

## 第18稿 — 頭を1枚のメッシュに。睫毛・涙線・強膜を実装

### 顔の継ぎ目を消した（構造の作り直し）

参考モデルは**顎から頭頂まで1枚の連続したクワッドメッシュ**。

パッチの境界が両頬に硬いシェーディングの線として出ていた。

パッチを**削除**し、シェル自身にレリーフを持たせた。そのために2つ必要だった:

- **サンプリング。** 超楕円のパラメータ化は角に頂点が集まり、**鼻のある平らな前面が最も粗くなる**。
  `a = u - 0.36·sin(2u)` で前後を3倍密にした（単調性は `a' = 1 - 0.72·cos2u ≥ 0.28` で保証）。
  結果、前面の頂点間隔 **2.2 mm**（参考の顔は4.0mm）
- **リング。** authored 14本を4倍に再サンプルして縦 **4.3 mm**

| | 参考 | こちら |

## 第20稿 — 体を1枚にする（SDF + surface nets + スキニング）

参考と並べたときの一番大きな差は顔ではなく**体**でした。
こちらは先細りの円柱の積み木で、**関節ごとに段差**がある。参考は1枚の連続した面。
これは調整では絶対に埋まりません——剛体パーツは定義からして連続にならない。

### 作り方

1. **SDF。** 骨格に沿った「楕円体で掃いた線分」の**滑らかな合併**（smooth-min）で体を定義する。
   骨格は**リグと同じ `JOINTS` から解いている**ので、フィールドとリグが食い違うことがない。
   楕円断面なのは、胴が幅より奥行きが浅いことを1種類のプリミティブで表すため。
2. **Surface nets。** 面を跨ぐセルごとに頂点1個、面を跨ぐ格子辺ごとにクワッド1枚。
   マーチングキューブスの256エントリの表が要らず、出力が**クワッド**になる。
3. **等値面への投影。** ニュートン法2回。9mmのセルだけだと階段状なので、ほぼ無料で効く。
4. **Taubin平滑化**（縮まない平滑化）→ もう一度投影。
5. **スキニング。** 各頂点を距離で最寄り4ボーンに束縛。CPUで変形して頂点バッファを書き戻す。

結果：**継ぎ目ゼロ**。鎖骨・三角筋・胸・くびれ・腸骨・臀部・腓腹筋が全部つながって出る。

### シルエットを実測して合わせた

両方のモデルの**幅 ÷ 身長**を高さごとに測ったところ、1回目はこちらが
**脚で20〜35%、腰で9%太かった**。滑らかな合併は接合部ごとに最大 k/4 だけ体積を足すのに、
半径をその分引いていなかった。全セグメントを実測値に合わせて引き直した。

### 首の段差

首の上端を**頭の中で終わらせる**ようにした。関節から28mm下では頭蓋の幅が64mmあるので、
34mmの首はそこで顎の下に消える。前は首が顎より太くて棚ができていた。

三角形数 66,000 → **90,608**（体が約35,000）。参考の体は28,000相当。

- GPUスキニング（今はCPU。ポーズ変更時のみ走るので静止では無料だが、アニメを入れるなら移す）
- 膝の皿、足の甲の形
- 服も骨に追従させる（今は袴・白衣とも剛体でヒップ／胸に固定）

## rigplay.html — 骨の入っていない OBJ に、骨を当てて歩かせる

手続き生成でリアリティを詰める方針の限界がはっきりしたので、**方向を変えました**。
既にある人型メッシュ（買ってきたモデル、スキャン、など）を読み込んで、
**自動でリグを組み、スキニングし、動かす**ツールです。

`python3 game/build_rigplay.py` で hiyorimi.html から生成します。レンダラは本編と同じ。

**モデルは同梱しません。** ブラウザに .obj をドロップすると、その場で解析します。
読み込みは全部ブラウザの中で完結し、どこにも送信されません。

### 骨格の推定

モデルについての事前知識はゼロで、**メッシュの形から測って**当てます。
仮定は「概ね直立」「x=0 について概ね左右対称」だけ。

| 部位 | 測り方 |
|---|---|
| 肩 | **\|x\| でスライス**して、各スライスの上下の高さが崩れる位置（胴のスライスは胴の高さ、腕のスライスは腕の太さ）。その上端＝肩峰から身長の1.8%下 |
| 肘・手首 | 肩から腕先までの **34〜51% / 68〜84%** を初期値とし、その範囲内に半径の極小が「内側に」あるときだけ補正 |
| 股下 | 高さバンドごとに**メッシュの連結成分を数え**、左右に並んだ2つの塊が中心線をまたいで離れている最も高いバンド |
| 足首 | 下から上へ走査して、断面が **z に長くなくなる**最初のバンド（足は前後に長い、脚は丸い） |
| 膝 | 足首〜股下で断面が最も細いバンド。**中点(52%)に寄せる重み**つき |
| 腰 | 股下〜肩で胴幅が最小。胴幅は \|x\| をソートして**身長の3.5%を超える隙間で切る**（最大値ではない） |
| 首 | 肩から身長の6.0%上。**幅では測らない** |

「胴の幅」は **\|x\| をソートして、隙間が身長の3.5%を超えたところで切る**ことで求めています。
これで、腕が真横に伸びていても胴だけを測れる。

### 外した測り方と、その理由

最初に書いた素直な測り方はほぼ全部外れました。実測して直したものを残しておきます。

- **「腕は水平だから、その高さを探せばいい」** — 実際の "Tポーズ" はたいてい A で、
  参考モデルの指先は身長の 60% にある。肩を 30cm 下に取っていた。
- **高さバンド 220 本** — 表面メッシュのリングは 0.8cm 間隔では疎で、空のバンドが出る。64 本に。
- **中心線の判定を \|x\| < 身長の1.4%** — 2.35cm は内腿を拾うので、脚のバンドまで
  「中心が詰まっている」ことになる。0.6% に。
- **中心線の判定を全頂点の比率で** — A ポーズは腰の横に手が来る。手は千頂点あって
  どれも中心線から遠いので、比率が薄まって**股下が腹の高さに上がった**。
  胴の柱に限って数えることで直った。
- **股下＝中心線に頂点がない最も高いバンド** — 低ポリゴンのモデルで壊れます。しかもそれは
  珍しい話ではなく、ダウンロードできるメッシュの大半がそうです。18角形の筒は、
  いちばん中心線寄りの頂点でも面から10°ずれた位置にあるので、**完全に詰まった胴でも
  中心線から1cm以内に何もない**ことがある。6,500頂点のテスト人型で、股下がウエストより
  13cm上に出ました。位相はテッセレーションに左右されません ── 脚2本はリング2つ、胴は1つ。
- **連結成分が2つあれば脚** — これも足りません。服を着たモデルは同じバンドに体のシェルと
  服のシェルがあり、それを脚と読みます（参考モデルの股下がウエストの16cm上に出た）。
  脚は**左右に並んだ**2つなので、x方向に中心線をまたぐ隙間があるかを見ます。
  服は体と x で重なるので、隙間はできません。
- **胴幅＝一定の窓の中の \|x\| の最大値** — A ポーズは腰の横に手が来るので、その高さでは
  手がいちばん幅広い。ウエストが股下より下に出ました。
- **膝＝最も細いバンド** — リングの断片しか入らなかったバンド（隣が50頂点なのに12頂点）が
  「非常に細い脚」として勝ってしまう。頂点数 18 未満は捨てる。
- **足首＝断面積が最小** — 足の面積は足首より大きいので、これはふくらはぎを見つける。
- **首＝肩より上で最も細いバンド** — 髪がちょうどその高さを占めていて、しかも肩より細い。
  毎回僧帽筋に着地する。首は身長の固定比で取るほうが遥かに堅い。

2つのモデルでの最終値（cm）。テスト用ダミーは `game/make_test_obj.py` が作る
5,700頂点の人型で、低ポリゴンでも壊れないことの確認用です。

|---|---|---|---|---|---|---|---|

### 指・顎・目 — 生きて見えるための3つ

上の7点は「体」を作りますが、**寄ったときに生きて見えるもの**は作りません。
握らない手と、動かない顔です。3つとも、メッシュへの残り方が違うので探し方も違います。

**指。** 最初に書いた「手を軸方向にヒストグラムを取って谷を探す」は動きませんでした。
実測したら理由は明快で、**脱力した手は指が接触している**うえ、
残った隙間は手のひらが埋めます。ヒストグラムは人差し指から小指まで一つの山でした。

分けられるのは**位相**のほうです。手を軸に沿って切り落とすと、
指の付け根より先で2本の指をつないでいるのは手のひらだけ ——
その手のひらを今切り落としたところです。連結成分がそのまま指になります。
ただし1回の切断では足りません。4本の指が分かれるのは手の 56% で、
親指はそこまで届いていない。だから**切断面を指先から下ろしながら掃引**して、
各指が「何かと融合する直前の最大の広がり」を記録します。

参考モデルでの結果：左右5本ずつ、親指（付け根 25%、長さ4.4cm）、
人差し〜小指（付け根 38〜46%、長さ 6.7 / 7.3 / 7.7 / 5.1cm）。中指が最長、小指が最短。

親指の判定は「扇の端にあり、かつ付け根がいちばん手首に近い」の両方です。
どちらか片方では足りません。「手首に近い」だけだと、手全体が早く始まるモデル
（全部の指が 0.22〜0.32 に収まる）で外れる。「端にある」だけだと、親指のない手で
小指が親指に昇格します。

**顎。** 顎の蝶番はメッシュのどこにも現れません（頭の内側にあります）。
頭のバウンディングボックスに対しては非常に予測可能な位置なので、箱のほうを測ります。
ただし顎ボーンの線分は頭の内側にあるので、**後頭部は顎から見て顎先と同じくらい近い**。
これを分けるものは幾何にはないので、「顎より上・顎より後ろは顎ではない」と明示しています。

**目。** 眼球はたいてい頭の中に浮かんだ独立したシェルです。
インデックスバッファ上の union-find で全シェルを列挙し、
小さくて・高くて・前にあって・左右対称なものを目とします。
目を顔に彫り込んだモデルからは何も出ませんし、それが正しい答えです。
見つかった目の頂点は**重み計算を通しません**（平滑化はメッシュのグラフ上を走り、
眼球は顔と辺を共有していないので、ぼかすと眼窩からずれていきます）。

指は**軸角**で回します。指のカール軸は世界軸ではなく手を横切る向きなので、
オイラー角で書くには腕全体を先にほどく必要がある。
その軸が必要な骨だけ、明示的な軸を持ちます。

### スキニング

**関節ではなく骨の線分**への距離で重み付け（前腕の点は肘にも手首にも近く、
その間の骨に属さなければならない）。左右の骨が反対側の頂点を掴まないよう、
符号違いにはペナルティを入れています。指は太さ15mm・隣まで20mmしかないので、
指だけ減衰指数を 4.5 → 9.0 に上げています。

そのあと**メッシュのグラフ上で2回平滑化**。距離だけだと肩に硬い境界線が走るので、
平滑化して初めて肩が「折れる」ようになります。

### スキニングは GPU で

ボーン行列を**1行の RGBA32F テクスチャ**に入れ、頂点シェーダで4本ブレンドします。
頂点属性が2本（ボーン番号・重み）増えるだけ。

1ポーズあたりの CPU 側の仕事：

| | 旧（CPU） | 新（GPU） |
|---|---|---|
| 毎フレームの変換 | 44,838頂点 × 4ボーン | 61行列 |
| 毎フレームの転送 | 頂点バッファ 1.61 MB | ボーンテクスチャ 3.9 KB |
| poseRig() 実測 | **8.41 ms** | **0.24 ms** |

ボーン数は 25 → 61 に増えているのに、35倍速くなっています。
（実測は同じページ・同じモデル・200回の平均）

なお、この変更は rigplay.html の生成時にシェーダへ差し込んでいるだけで、
hiyorimi.html 本体には入れていません。本編のキャラクターはポーズごとに
**作り直している**ので、別の問題です。

### アニメーション

手続きのサイクル（立ち・歩き・走り・跳び）。T字ポーズで来たモデルは、
まず腕を72°下ろすところから始まります（腕が既に下りていれば0に近い）。

膝は**片方向にしか曲がらない**ようクランプし、足が地面を離れた直後に最も曲がる位相にしています。

手は歩・走・跳でそれぞれ握り方が変わります（走りはほぼ拳、跳びは開く）。
親指だけは 40% しか閉じません —— 全部の指を同じ角度で曲げると鉤爪に見えます。

目は**サッケード**です。止まっていて、跳ぶ。滑らかにパンする目は、
顔にできることの中でいちばん不気味です。

### 制限

- 腕が**真横に伸びている（T字/A字）**前提。腕を完全に下ろしたモデルは肘・手首の推定が外れます
- 指が接触したまま閉じているモデル（拳・ミトン）からは指が出ません。
  出ないときは手が丸ごと1本の骨として動きます
- まぶたは動きません（眼球シェルは見つかりますが、まぶたは顔の一部で分離できない）
- 表情は顎だけ。頬・眉・口角のボーンは入っていません

## blender_autorig.py — Blender で正しくリグする

`rigplay.html` と同じ方法で関節を推定し、**その先を Blender に任せる**版です。

    blender --background --python game/blender_autorig.py -- model.obj out.glb
    python3 game/blender_autorig.py model.obj out.glb        # bpy モジュール版

同じスクリプトが手元の Blender でも動きます（GUI の Scripting タブに貼っても可）。

### 何が変わるか

スキンウェイトを、私が書いた「骨の線分までのユークリッド距離」ではなく
**Blender のヒートマップ自動ウェイト**（Bone Heat Weighting）が決めます。
あれは**表面上の測地距離**で熱拡散を解いていて、別物です。
肩を46°下ろしたときに三角筋が痩せない ── これが本命の差です。

関節の推定は JS 版と**完全に一致**します（正規化の差を戻すと全項目同じ）。

| | 足首 | 膝 | 股下 | 腰骨 | ウエスト | 肩 | 首 |
|---|---|---|---|---|---|---|---|
| JS (rigplay.html) | 9.2 | 48.5 | 82.5 | 90.1 | 108.7 | 128.1 | 138.1 |
| Python (Blender) ×1.0164 | 9.2 | 48.5 | 82.5 | 90.1 | 108.7 | 128.1 | 138.1 |

### ヒートマップは、そのままでは掛からない

熱拡散は表面上で解くので、**表面がひと繋がりでないと解けません**。
参考モデルは **1,412 個の別々のシェル**でできていて（髪の房、服のパネル、
眼球、まつ毛…）、最大の塊でも全体の 30% しかありません。丸ごと渡すと
Blender は解を見つけられず、**39個の頂点グループを作ってどれにもウェイトを
入れずに終わります** ── 一見成功したように見えて、動かないリグができます。
実測：重複頂点をマージし法線を計算し直しても、境界辺が 23,657 本残り、
やはり 0/39 でした。

なので**体の本体にだけヒートマップを掛け、残りのシェルは最寄りの体表面から
転写**します（近傍3点の距離逆数で混ぜて、境目が硬くならないように）。
これはリガーが髪や服に対して実際にやることでもあります ──
髪は頭の動きに従うべきで、髪自身の熱拡散に従うべきではない。

    連結成分 1412 個、本体は 13388 頂点 (30%)
    ヒートマップ: 13388 / 13388 頂点にウェイト
    スキニング完了: 44838 / 44838 頂点にウェイト

### この環境について

Blender 5.0.1 を Python モジュール（`pip install bpy`）としてヘッドレスで
動かしています。使えることを実測で確認したもの：モディファイア、
**布シミュレーション**（40フレームで 1.21 落下しコライダーに沿って変形）、

### 歩行サイクル

`walk_cycle()` が歩行をキーフレームで焼き、glTF に一緒に書き出します
（33フレーム、最後のフレームは最初と同じ姿勢＝ループ）。

**関節角を直接振る方式は捨てました。** rigplay.html と同じ設計（腿を24度、
膝を46度…）で焼いて実測したら、あれは歩いていませんでした：

    足首の最低高 0.080 m に対して最高 0.186 m（静止時 0.090）
    接地とみなせるのは 33 フレーム中 5 フレームだけ
    その 5 フレームの間に 0.188 m 滑っている

腿と膝の角度を決めて振ると、**その合計がどこに足を置くのかを誰も見ていない**。
足は宙に浮いたまま、地面の上を滑ります。

なので**足の軌道のほうを決めて、股と膝の角度を逆運動学で解きます**。
立脚中の足首は接地したまま一定速度で後ろへ流れ（その場歩きなので、地面の
ほうが後ろへ流れると解釈する）、遊脚中に持ち上がって前へ戻る。

真っ直ぐな脚のままでは足を前後に置けません ── 直立時点で脚は伸び切って
いるからです（股 0.870 − 足首 0.090 = 0.780 = 腿+脛）。**骨盤が下がるのは
そのため**で、実際の歩行でも 30〜50mm 下がります。

逆運動学で解いたあとの実測：

| | 値 |
|---|---|
| 足首の最低高 | 0.090 m ＝静止時とぴったり一致（接地している） |
| 接地フレーム | 21 / 32（65%、立脚割合の設定 62% と一致） |
| 1歩の長さ | 0.424 m |
| 接地中の1フレームあたりの後退量 | −0.018 〜 −0.022 m（ほぼ等速＝滑っていない） |
| 膝の曲がり | 18° 〜 67° |
| 骨盤の上下動 | 0.041 m |
| 手首の前後振れ幅 | 0.318 m |

**腕を振る軸は X ではなく Z です。** 休めの姿勢で腕は真横を向いているので、
そこで世界 X まわりに回しても腕が**捻れる**だけで前後には振れません
（実測：手首の振れ幅が 0.028 m しかなかった）。真横の腕を前後に振る軸は
鉛直の Z で、腕を体側へ下ろすのはその後。肘も同じ理由で Z まわりです。

**ボーンのローカル軸を番号で決め打ちしてはいけません。**ローカル軸は骨の向きと
ロールで決まるので、腿と上腕と指では「前後に振る軸」が別々の番号になります。
番号を書くと、腕を振ったつもりが捻れる。`axis_of()` が世界軸（左右=X、
前後=Y、上=Z）から骨ごとに引き当てます。

書き出した GLB の中身（実測）：

    animations: 1  name=walk  channels=118
    skins: 1  joints: 39
    nodes: 41  meshes: 1

Blender 4.4 以降のアクションは**スロット付き**で、F カーブは
`layers/strips/channelbags` の下にあります（`act.fcurves` は空）。
`action_fcurves()` が両方の API に対応します。

### 「歩いてはいるが不自然」の中身

逆運動学で足は着いたものの、まだ不自然でした。足りていなかったのは以下です。
どれも歩行の教科書に載っている話ですが、**入れるまで何が欠けているのか
言葉にできませんでした** ── 入れて比べて初めて分かる種類のものです。

- **足の転がり。** 立脚のあいだずっと足裏が地面と平行、というのがいちばん
  大きな違和感でした。踵接地（爪先が9°上）→ 足裏全接地 → 蹴り出し（26°）。
  蹴り出しでは踵が浮くので、足首は爪先を軸に 55mm 持ち上がります。
- **足幅。** 骨盤と同じ幅の2本のレールの上を進んでいました。実際の歩行の
  足幅はもっと狭い。股から足首までを3次元で解いて（横方向は世界 Y まわりの
  開き、残りを矢状面の2骨 IK に渡す）、足幅を骨盤幅の 55% に。走りは 35%。
- **骨盤の傾き（トレンデレンブルグ）。** 遊脚側が 4° 下がる。
- **左右への体重移動。** 骨盤が立脚側へ 20mm 寄る。これがないとレールの上を
  滑っているように見えます。
- **頭の安定化。** 胸の捻れを首で打ち消して、頭は進行方向を向いたまま。
- **肘。** 腕が前に出るときだけ曲がりが増える。

**滞空ぶんの高さを IK にだけ渡して骨盤に渡していなかった**バグもありました。
走りで足が 2cm 地面にめり込んでいた（足首の最低高 0.069、静止時 0.090）。
骨盤の実際の移動量は、IK に渡した股関節の高さと同じでなければなりません。

### まだ無いもの

**方向転換のクリップはありません。** ゲームでは走行時にルートを回すのが
普通なので、`walk` を再生しながらルートの向きを変えてください。その場での
向き変え（足を踏み替えるピボット）は別途必要なら作れます。
横歩き、しゃがみ、階段、坂道への足の適応（IK の接地補正）も未着手です。

### 世界軸をボーンのローカル軸に「丸めて」はいけない

最初の `local_axis()` は「世界軸に一番近いローカル軸に丸める」実装でした。
これは間違いで、実測で出ました。

    腕の軸が世界 Z から数十度ずれていたせいで、振るたびに前へ流れ、
    歩行中ずっと手が体の前 +0.12〜+0.33 m にあった。
    左右にも肩より 0.18 m 外へ張り出していた（体の半幅は 0.148 m）。

丸めずに、世界軸をそのままボーンのローカル座標へ変換します
（`matrix_local.to_3x3().inverted() @ world_axis`）。1行の違いですが、
腕の挙動がまるごと変わりました。

| | 肘の曲がり | 手が肩より外へ | 手の前後 |
|---|---|---|---|
| idle | 26° → 17° | +0.112〜+0.169 → +0.086〜+0.130 | +0.138〜+0.160 → −0.031〜−0.001 |
| walk | 22〜28° → 31〜34° | +0.164〜+0.181 → +0.033〜+0.139 | +0.121〜+0.326 → 0.000〜+0.241 |
| run | 22〜32° → **76〜88°** | +0.077〜+0.184 → **−0.137〜+0.036** | +0.067〜+0.326 → +0.019〜+0.228 |
| jump | 48〜69° → 40〜62° | +0.021〜+0.137 → −0.091〜+0.068 | −0.146〜+0.354 → −0.247〜+0.221 |

走りの肘が 22〜32° しか曲がっていなかったのも同時に直しました
（走者の肘は 90° 近くまで曲がります）。クリップごとに基準値を持たせ、
腕が前に出るときだけ深くなるようにしています。

### 表情

`face_shapes()` が顔をシェイプキーで作ります。glTF ではモーフターゲットに
なるので、実行時に 0〜1 で混ぜられます。

    morph targets: 7
    ['blink', 'smile', 'mouth_open', 'brow_up', 'brow_down', 'eye_wide', 'cute']

`cute` は表情ではなく**顔の寄せ**です。目を大きく少し下げ、目の開口部を
それに合わせて広げ、鼻を控えめにし、顎を細く短くし、目より上の頭をわずかに
大きくする。0〜1 のスライダーなので、どこまで寄せるかを後から決められます。
他の表情と混ぜられます。

#### 顔のパーツをどう見つけるか

目は独立したシェルなので連結成分で拾えます。残りは目と頭の箱からの比率。
実測（参考モデル、身長1.65m 正規化）：

    目の中心 (±0.040, 1.469, 0.054)  半径 0.024
    中心線の前面 z : 1.422 で極大 0.104（鼻先）
                    1.462 で極小 0.082（鼻根・眼窩）
                    1.522 で極大 0.115（額）

**アニメ顔では額が鼻より前に出ています。**「いちばん前の点＝鼻先」という
素直な探し方は、この種のモデルでは額を拾います。目より下にある極大を取ります。

#### 目のあたりには板も球もある

最初は大きさだけで選んでいて、**まつ毛の板を「目」と呼んでいました**。
目の周りのシェルを並べると：

    187頂点  (±0.047, 1.477, 0.067)  0.061×0.029×0.031  細長 ← まつ毛
    165頂点  (±0.050, 1.456, 0.064)  0.053×0.018×0.026  細長 ← アイライン
    162頂点  (±0.040, 1.469, 0.055)  0.049×0.049×0.048  球状 ← 眼球
     95頂点  (±0.041, 1.465, 0.061)  0.041×0.023×0.019  細長 ← 虹彩

球状（最大寸法/最小寸法 < 1.7）のものを目の中心とし、その周りのシェルを
まとめて目のグループにします。まとめないと、目を大きくしたときに眼球だけ
広がってまつ毛が置き去りになります。

眼球の拡大は控えめ（10%）にして、開口部のほうを大きく広げています。
眼球を 20% 広げたら、まぶたの開口部からはみ出しました。

#### 残っている制限

- **マテリアルと UV は落ちています。** 自前で OBJ を読んでいるので
  `usemtl` を見ていません。書き出した glb は形とボーンと表情だけで、
  色は付いていません（上の絵は確認用に眼球へ手で色を当てたものです）
- 口の位置は顎と鼻先からの比率で置いています（chin + 0.44×(nose−chin)）。
  唇の稜線を直接探してはいません
- 舌・歯・まぶたの裏はありません。大きく口を開けると中が見えます

## shrineplay.html — 神社のワールドでキャラクターを操作する

    python3 game/build_shrineplay.py

伏見稲荷のワールドはそのまま、視点を三人称にして、リグ済みの `.glb` を
ドロップするとそのキャラクターを操作できます。`blender_autorig.py` が
書き出したものがそのまま使えます。モデルは同梱していません。

`hiyorimi.html` には手を入れず、生成時に差し込んでいます。移動・当たり判定・
地面追従は**本編のコードをそのまま使っています** ── 一人称のカメラ位置を
プレイヤー位置として扱い、そこから後ろへカメラを引いているだけです。

| | |
|---|---|
| WASD / 矢印 / スティック | 移動（速度で idle→walk→run が切り替わる） |
| Shift | 走る |
| マウスドラッグ | カメラ |
| Esc | 案内を消す |

### glTF をどこまで読むか

`parseGLB` → アクセサ（`byteStride` と `sparse` に対応）→ スキン
（`inverseBindMatrices`、ジョイントのノード列）→ ノード階層の TRS →
アニメーション（LINEAR、回転は slerp）→ モーフターゲット。
スキニングは頂点シェーダ、ポーズは1行の RGBA32F テクスチャ。

    ボーン 39 / クリップ idle,jump,run,walk / 44,838 頂点 / 表情 7

### 表情の置き場所は、頂点番号の散らばりで決まる

モーフは「影響する頂点の範囲だけ書き戻せばいい」と思っていました。実測：

    表情が動かす頂点  29,063 / 44,838   連続した区間 945 本

`cute` が頭と髪ぜんぶを動かすからです。`cute` は表情ではなく**静的な設定**
なので、読み込み時に一度だけ頂点へ焼き込むことにしました。残りは 13,731。

それでもまだ駄目でした。**まばたきの影響頂点は数百なのに、その頂点番号が
メッシュ全体に散っている**（最小から最大まで 35,069 頂点ぶん）。連続範囲で
更新する作戦は、このメッシュでは成立しません。

なので**まばたきだけ頂点属性**（location 11）に持たせ、重みを uniform で
渡します。1フレームぶんの費用は uniform 1本ぶん。残りの表情
（smile / mouth_open / brow_up / brow_down / eye_wide）は滅多に変わらないので
CPU 側の書き戻しのままです。

### モデルを埋め込んで1枚にする

    python3 game/build_shrineplay.py model.glb          -> shrine_game.html

引数に .glb を渡すと、base64 で本文に埋め込み、**ドロップの案内ごと削除**して
起動時に自動で読み込みます。開いたら即遊べる1ファイルになります
（4.8 MB の glb → base64 6.3 MB、ページ全体で 6.7 MB）。

生成物はリポジトリに入れていません（買ってきたモデルを含むため）。
引数なしで実行すればドロップ版の `shrineplay.html` が出ます。

### ジャンプとクロスフェード

上下方向は世界側に無いので、プレイヤー側で持っています（初速 5.4 m/s、
重力 18 m/s²、頂点 0.63 m、滞空 0.6 秒）。滞空中はサイクルを止めて
jump クリップの姿勢で保持します。

クリップの切り替えは、前のクリップを止めた瞬間の姿勢を覚えておいて
0.16 秒かけて混ぜます。瞬時に切り替えると足の入れ替わりが跳ねます。

フレームごとの実測（ジャンプ）:

    jump y=0.00 air=1 fade=0.10      <- 踏み切り、混ぜ始め
    jump y=0.45 air=1 fade=-0.02
    jump y=0.63 air=1                <- 頂点
    jump y=0.13 air=1
    idle y=0.00 air=0 fade=0.10      <- 着地、idle へ混ぜ戻す

### カメラの位置を、次のフレームの入力にしてはいけない

三人称にした最初の版は、**世界の下へ抜けていきました**（地面が消えて空中に
浮いているように見える）。原因はプレイヤーの位置ではなく、位置の持ち方です。

本編の移動コードは `CAM.pos` を「プレイヤーの目の位置」として読み書きします。
三人称化でその `CAM.pos` をカメラ位置（3.1m 後ろ、目線より上）に書き換えたので、
**次のフレームの移動計算がカメラ位置に対して行われる**ようになりました。
毎フレーム、後退ぶんと高さの差が位置に足し込まれ続けます。

    毎フレーム  y ← y + 身長の82% + 0.22 − 目線の高さ  ≒ −0.047 m

`updateCamera` の頭で、カメラに書き換える前の位置へ戻すようにしました。
移動も接地もプレイヤーに対して行い、カメラの後退は描画のためだけに使います。

修正後の実測（歩行中）:

    player=3.02,-4.29,-74.17  地面=-4.30  足元の差=+0.007
    player=3.02,-4.30,-75.63  地面=-4.30  足元の差=-0.002
    player=3.02,-4.32,-76.39  地面=-4.30  足元の差=-0.022

足元の差が歩行の上下動ぶん（±2cm）に収まっています。

- テクスチャは読んでいません。粘土色（`PLAY_TINT`）で置いています

キョンシーは出しません（`spots` を空に）。代わりに**同じモデルの参拝客**が

**1回の描画で全員べつの姿勢を取ります。** ボーンのテクスチャを1行から
複数行にして、頂点シェーダが `gl_InstanceID` で自分の行を読みます。
インスタンス 0 が自分、1 以降が参拝客。

## 第22稿 — 残していた3つ（分岐・群衆の間引き・沢と眺め）

前回「設計は決まっているが手が入っていない」として残した3つを入れました。
先に、それを入れる前に見つかった不具合を2つ書きます。どちらも**世界が
見えない**という種類のもので、地形をいじる前に直す必要がありました。

### 世界がまるごと消えていた（サンプラの型衝突）

`shrineplay.html` を**モデルを落とさずに開くと、空しか描かれません**。
地面も鳥居も出ません。

原因は GPU スキニングを差し込んだときの取りこぼしでした。頂点シェーダに
足した `uniform sampler2D uBones` は、テクスチャユニットを指定しない限り
0 番を指します。0 番は `uMatA`（`sampler2DArray`）が使っています。
**同じユニットを型の違うサンプラが共有している描画は、WebGL が
`GL_INVALID_OPERATION` で捨てます。**

    [.WebGL] GL_INVALID_OPERATION: glDrawElementsInstanced:
             Two textures of different types use the same sampler location.

`uBones` を割り当てていたのは骨のある描画だけ（`if (d.skin) tex(...)`）
だったので、モデルを落とすまで一度も 6 番に移らず、その間の描画が全部
落ちていました。モデルを落とすと、キャラの描画が 6 番に設定した次の
フレームから世界が出ます。落とさずに歩けるはずの遊び方が壊れていた
わけです。骨の有無にかかわらず毎回ユニット 6 を割り当て、骨が無いときは
1x1 のダミーを差すようにしました。

### 新池は一度も見えていなかった

`POND` は水面の円盤を参道から横 15.5m・下 1.05m に置いていました。
その位置の地形の高さは `bankHeight(15.5)` = **路面より 10.72m 上**です。
池は山の中に 11.8m 埋まっていました。

さらに、円盤の三角形の巻き方が `(中心, ring[i], ring[i+1])` で、面法線が
**-Y** を向いていました。頂点法線は +Y を入れてありますが、裏面カリングが
見るのは巻きだけです。掘り出しても、上からは見えないままでした。

両方直してあります。

### 1. 参道の分岐

`bankHeight(s)` は「中心線からの距離」だけで高さを返していました。この形の
まま分岐は作れないので、`t` を受け取れるようにして、**2本の参道のうち近い
ほうからの距離**で土手を作ります。すると2本のあいだに土手が1本残り、それが
そのまま仕切りになります。

    分岐区間の断面（t=52、路面からの高さ）
    s=-1.6:0.07  0.0:0.00  1.6:0.16  2.4:0.86  3.2:0.89  4.0:0.23
    s= 4.8:0.13  5.6:0.16  7.2:0.31  8.0:1.01  8.8:1.76

幅 3.2m の道が2本、あいだに高さ 0.9m の土手。実物の千本鳥居の二列と同じ
断面になりました。横のずれ `off(t)` は t=30 と t=75 で 0、その間は平行で、
両端は smoothstep なので**傾きも 0**になります（折れ目が出ない）。

鳥居は両方に立てます（分岐側 53 基）。ただし分岐側は別メッシュにしました。
太陽の遮蔽モデルが読むのは中心線の `R.toriiTs` で、そこに第2の道の鳥居を
混ぜると、影の計算が二重に暗くなるからです。

歩ける帯も広げました。もとは中心線から左右対称に `corridorHalf` で押し
戻していたので、分岐へ入った瞬間に中心へ引き戻され、道があるのに歩けません。
帯を `[-half, off+half]` にしています。参拝客も 45% が第2の道へ流れます。

敷石は分岐側にも敷きました。本体の舗装は中心線 ±1.45m にしか無いので、
そのままだと第2の道は苔の上になります。重なる区間（分かれ目と合流点）は
幅を 0 に絞ります —— 重ねると z 争いでちらつくので。

### 2. 群衆の間引き

本命の対策です。参拝客が主人公と同じ **62,824 三角形**なのが負荷の根本
原因でした。Blender の Decimate で作った版を持てばいいのですが、モデルは
遊ぶ人が落としてくるので、**読み込み時にこちらで作る**ことにしました。

頂点クラスタリングです。格子を切り、同じマスに落ちた頂点を代表点へ潰し、
潰れた三角形を捨てます。O(N) で終わります。骨の番号と重みはマスの代表
頂点のものを引き継ぐので、**同じボーンテクスチャでそのまま動きます**。

描画は2つに分けました。手前 6 人は本メッシュ、その先は間引きメッシュ。
ボーン行列は1枚のテクスチャの行に詰めたままで、遠い人の描画は
`uRowBase` で読む行を頭出しします（0=自分 / 1..6=手前 / その先=遠く）。

本番のモデル（44,838 頂点 / 62,824 三角形 / 骨 39 本）での実測:

    間引き 62,824 三角形 -> 1,956 三角形（32.1分の1）
    t=120  近6人/遠 4人   447,592 三角形（全員を本メッシュなら   691,064）
    t=250  近6人/遠10人   459,328 三角形（全員を本メッシュなら 1,068,008）
    t=400  近6人/遠15人   469,108 三角形（全員を本メッシュなら 1,382,128）

**前の版は 14 人で打ち切って 942,360 三角形**でした。いまは 21 人出して
469,108 三角形です。人数が 1.5 倍、三角形は半分になりました。打ち切りは
14 人 → 26 人に上げてあります。

間引き後の枚数は元の枚数ではなく**表面積**で決まるので、モデルが重いほど
比率は上がります（検証用の 6,160 三角形のモデルでは 4.5 分の1 でした）。

### 3. 沢と、四ツ辻からの京都市街

**沢**は t=193〜242、新池に注ぐまでの 49m。地形に幅 3m・深さ 1.2m の溝を
掘り、その底を追いかける水面のリボンを張ります。高さは下流へ向かって単調に
下がるよう締めてあります（1箇所でも上を向くと水が坂を登って見えます）。
水際には石を 88 個。木と下草は溝の中には生やさず、**樹冠は水の上を抜いて**
あります —— 覆われていると水面に映るものが無く、ただの暗い面になるので。

新池は掘り直しました。ここで一度間違えています。**池の中心からの半径で
掘ろうとした**ところ、参道は池から 16m 離れているので路肩の手前で効果が
消え、参道と水面のあいだに高さ 5m の壁が残りました。池は相変わらず
見えません。半径ではなく**断面**で掘るのが正しい:

    新池の断面（t=182、路面からの高さ）
    s=0:0.00  2:0.43  4:0.14  6:-0.55  8:-1.17  10:-1.35 … 22:-1.35
    s=24:0.05  26:4.02  28:9.61  30:15.57

路肩から水際までなだらかに落ち、水面（-0.75）は目の高さより 2.35m 下。
対岸で山へ戻ります。

**京都市街**は幾何としては置けません。霧の見通しは 1/fogDensity ≒ 80m
しかないので、何km も先の街をメッシュで置いた瞬間、合成パスが真っ白に
塗り潰します。近くに縮小して置けば視差が嘘になります。

なので**空として描きました**。深度が遠クリップのままの画素（= 空）は
ライティングパスで色が決まり、そのあとの霧の対象になりません。仰角で
3つに切り分けます:

| 仰角 | 何 |
|---|---|
| 稜線（+1.6°〜+3.4°、方位で揺らぐ）より上 | 空 |
| 稜線から地平まで | 西山。空の色 × (0.44, 0.52, 0.68) |
| 地平のすぐ下（-0.2°〜-1.2°） | 京都盆地。区画くらいの粒を乗せる |
| その下 | 手前の山。霧色へ繋ぐ |

色は**その画素の空に掛けて**作ります。定数で置き換えると時刻に追従しません
が、掛け算なら朝焼けにも夕景にもそのまま乗ります。夜は `uStarAmt` で街の
灯りが点きます。出るのはカメラが稜線より上（y>17m）に出たときだけ。石段を
登りきると街が開ける、という順番そのものがこの区間の意味になります。

見えるようにするために、地形のほうも3つ直しました。

- **西を落とす。** 街は WNW ですが、参道は ENE に登るので、世界座標では
  **+X・-Z**、登る自分から見て「右うしろ」です（`R.cityDir` が
  `(+0.707, 0, -0.707)`）。ここを取り違えて、最初は反対側を落としていました。
- **路肩を下げる。** 落とし始めを横 3.0m にしていたときは、路肩に高さ 2m の
  土手が残り、それが仰角 +5° を塞いでいました。街の帯は地平のすぐ下なので、
  路肩が目の高さを越えた時点で何も見えません。2.1m から落とすようにしました。
- **扇形に伐り開く。** 斜面を落としても木立が塞ぎます。かといって区間まるごと
  坊主にすると伐採跡になります。四ツ辻から街の方角へ開く扇（遠いほど広い）
  だけを抜きました。

地形メッシュは横 46m で終わるので、切り口が直線で空に接しないよう、落ちて
いく斜面をもう一枚（裾）伸ばしています。**この裾は見晴らしが開いている t
だけ外へ伸ばします。** 一律に伸ばしたときは、掘っていない区間の土手がその
まま伸びて 100m 先に高さ 50m の壁が立ち、四ツ辻から見ると視界の下半分が
霞んだ茶色で埋まりました。

### 統合版（モデル埋め込み）で確認したこと

`shrine_game.html` はリポジトリに入れていないので、手元の `.glb` から
毎回作り直す形になります。今回、上のモデルを埋め込んだ版で通しました。

    python3 game/build_shrineplay.py character.glb game/shrine_game.html
    -> 6.7 MB（glb 4.76 MB -> base64 6.34 MB）

念のため、変更前のソースから同じ .glb で組み直したものと、手元にあった
統合版を突き合わせています。モデル部分を除いて**差分 0 行**でした。
`shrineplay.html`（ドロップ版）と `shrine_game.html`（埋め込み版）は同じ
`build_shrineplay.py` の出力なので、片方だけに入る変更はありません。
