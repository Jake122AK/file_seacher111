# 日和見 — 太陽プロトタイプ

伏見稲荷・千本鳥居を舞台にした「時刻パズル」の第一プロトタイプ。
`hiyorimi.html` をブラウザで開くだけで動く（WebGL2 必須、外部依存ゼロ）。

## このプロトタイプが証明しようとしていること

企画全体の生死を分ける問いは一つだけ:

> **ダイヤルを回して影が動くのは、それ自体が気持ちいいか？**

ここが No ならパズルもナラティブも意味がない。

第一版は太陽の挙動と手触りだけだった。第二版でキョンシーを入れ、
**その太陽が武器になる**ところまで通した（下の「キョンシー」節）。

## 中核の設計判断 — 太陽を「2本のスライダー」から「暦」に変えた

元の描画エンジンは太陽高度と方位が独立した自由スライダーだった。それでは
パズルにならない。自由度が高すぎて総当たりで解けてしまうからだ。

かわりにプレイヤーが握るダイヤルは2つだけ:

| ダイヤル | 範囲 | 意味 |
|---|---|---|
| **節気** | 二十四節気 24段 | 太陽が描く弧の**形**が変わる |
| **時刻** | 0:00–24:00 連続 | その弧の上のどこにいるか |

高度と方位はこの2つと**緯度 34.9671°N から天文計算で一意に決まる**
(`c2_astro.js` 節)。結果として:

- **到達できない太陽位置が生まれる。** 京都で「真北から低く差す光」は
  一年のどの瞬間にも作れない。これが物理的な壁になり、パズルが成立する。
- **夏至と冬至が極点になる。** 影が最も短い日と最も長い日がゲームの
  「最強の道具」として暦の両端にあり、そこへ至る動機になる。
- **午前と午後で同じ高度が2回来る。** 方位は鏡像、光の色も違う。
  「高度は合っているのに解けない」という良質な引っかかりが自然発生する。

### 実装した天文

二十四節気は黄経15°ごとに正確に並ぶので、節気の番号だけから赤緯が閉じた式で
出る（暦テーブル不要）。均時差と経度差（明石135°Eとの0.77°）も入れてある。

検証値（`node astro_test.js` 相当）:

| | 日の出 | 南中 | 日の入 | 南中高度 |
|---|---|---|---|---|
| 春分 | 06:01 | 12:05 | 18:09 | 55.03° |
| 夏至 | 04:43 | 11:58 | 19:13 | 78.47° |
| 秋分 | 05:46 | 11:50 | 17:54 | 55.03° |
| 冬至 | 07:01 | 16:49 | 16:49 | 31.59° |

実際の京都の暦とのずれは**1〜3分**。南中高度は理論値
(90° − 緯度 ± 23.44°) と小数点以下まで一致する。均時差が効いているので
春分の南中は 12:05、秋分は 11:50 と正しく非対称になる。

### 参道の方位

世界座標 +Z（参道が登る方向）の方位を **75°（ENE）** に設定した。
実際の千本鳥居が東北東に登るのに合わせてあるが、同時にゲーム上の判断でもある:

- 春分・秋分の日の出（方位 89.6°）は**参道をまっすぐ射抜く**
- 夏至は 60.5°、冬至は 118.5°

つまり**一年をかけて日の出が参道の軸を横切る**。これがそのままパズルの
主軸になる。

## 手触りのための実装

- **ダイヤルは目標値。太陽は臨界減衰でそれを追う。** フレームレート非依存
  (`dampWrap`)。時刻は λ=5.5、節気は λ=3.2 と重くしてある（暦が動くのは
  儀式的であってほしい）。真夜中をまたぐときは短い方向に回る。
- **IBL は毎フレーム焼かない。** 太陽の直射（＝影と鏡面）は毎フレーム
  更新するが、環境光キューブは角度が 0.32° 動いたときだけ、しかも
  掃引中は2フレームに1回に間引く。目が追うのは影であって環境光ではない。
- **TAA は太陽が動いている間だけ履歴を捨てる** (`0.88 → 0.54`)。
  動く影に対する TAA ゴーストはパズルゲームでは致命傷になる。
- `T` で早送り（一日 ≈ 28 秒）。`Q`/`E` で時刻、`Z`/`X` で節気。

## グラフィック側で書き直した部分

太陽が一日中どこにでも行けるようになった以上、夕暮れ専用に手で調整された
ライティングは通用しない。物理から出るように書き直した。

- **太陽の色は美術指定ではなく大気の透過率**。天頂での Rayleigh + Mie
  光学的厚さに相対エアマス（Kasten-Young）を掛けて指数を取る。この一本の式
  だけで、南中は暖かい白 (9.9, 9.3, 8.0)、地平線際は深い赤 (1.1, 0.31, 0.01)
  になる。手描きのグラデーションは一切ない。
- **自動露出は実測**。ここは一度作り直した。最初は太陽高度から露出を
  推定していたが、**屋根のある回廊の中では太陽が高いほど目に届く光は
  減る**（笠木が遮る）。開ループ推定は、暗くなった瞬間に絞りを絞る。
  実際に南中の絵が真っ黒になった。
  かわりに描画済みフレームを測る:中央重点の平均輝度を 1×1 のターゲットで
  適応させる（Reinhard 平均。log 平均はこのシーンの真っ黒な領域に
  引きずられて昼夜の差が 1.5 倍しか出なかった）。**読み戻しもストールも
  ない**。明順応は速く (τ≈0.7s)、暗順応は遅く (τ≈1.8s)。
  **完全な正規化はしていない**——`pow(L, -0.75)` にして、夜は夜として
  暁の約 70% の明るさに見えるようにしてある。真夜中と真昼が同じ明るさに
  なるのが自動露出の典型的な失敗なので。
  スライダーは絶対値ではなく**補正**に変えた。ブルームの閾値も露出に
  追従させてある（さもないと南中で画面全体が滲む）。
- **夜**。地平線下でも破綻しないよう、大気光の底と**京都の街明かり**
  （方位300°の地平線、雲の底を舐める）を空シェーダに追加。
- **星**。天球に固定した3オクターブの星野を、天の北極まわりに時角ぶん
  回している。つまり夜のあいだ星は正しく東から昇る。キューブマップに焼くと
  エイリアスするので、空ピクセルに解析的に描いている。
- **石灯籠**は太陽が沈むにつれ点る（点光源と自己発光の両方）。

## キョンシー — 追跡と戦闘

### なぜキョンシーなのか（技術的な理由）

このエンジンにスケルタルアニメーションは無い。人型を歩かせるのは本来苦手。
しかし**キョンシーは硬直したまま跳ねる**のが定義的な動き — 死後硬直で膝も肘も
曲がらないから、両腕を前に突き出したまま跳んで移動する。つまり
**剛体のまま animate できる**。弱点が仕様になる、数少ない題材。

実装は4つの剛体パーツを手組みの階層に乗せただけ:

| パーツ | 三角形 | 動き |
|---|---|---|
| 体（官服・帯・朝靴） | 960 | 跳躍アーク + 着地スカッシュ |
| 頭（頭蓋・辮髪・官帽） | 1188 | 体に遅れて追従（バネ）+ ゆっくり首を振る |
| 両腕（袖・拳） | 544 | 体にさらに遅れて追従 |
| 符 | 40 | 跳躍の上下加速度で駆動される振り子 |

跳躍サイクルは 沈み込み → 跳躍 → 滞空 → 着地 → 整い の5段階で、
**前進は滞空中にしか起きない**。これが「跳んでいる」ように見えるか
「滑っている」ように見えるかの分かれ目。

### 戦闘 = 暦

キョンシーは**直射日光で焼ける**。つまり武器は節気と時刻のダイヤルそのもの。
ある一体を祓うには「今その位置に光が届く時刻はいつか」を暦から割り出す。

日光判定は、影マップを読み戻せないので鳥居列の解析モデルに対して太陽光線を
マーチする。参道の z 座標がそのままパラメータで、接線が +Z から18°以上
外れないので、最近点を解かずにローカル座標が取れる。梁の占有は5cm刻みの
ルックアップに焼いてあるので1サンプル数命令。

実測した「光が届く場所」（横方向オフセット別、`.` は日陰）:

```
             lateral:  -1.0   0.0   1.0
春分  7:00  el 11.3    0.74    .     .
春分 12:00  el 55.0    0.85   0.99  0.90
夏至 17:00  el 24.6     .      .    0.90
秋分  6:00  el  2.1     .     0.28   .
冬至  9:00  el 18.3    0.85   0.83  0.73
冬至 12:00  el 31.6    0.85   0.99   .
```

季節と時刻の組み合わせごとに**答えが違う**。南中は回廊の中央まで光が落ちる
（高い太陽は梁の隙間を抜ける）が、冬至の低い太陽は片側にしか届かない。
夜はどこにも届かないので、夜は戦えない — 逃げるしかない。

キョンシーは |横方向| < 1.55 の範囲、つまり柱の内側に留まるので、
上の表の3列が実際に意味を持つ列になる。

### その他

- 接触すると**呪い**が溜まる。溜まるほど画面から彩度が抜け、赤に寄り、
  周辺が落ちる。満ちると参道を16m引き戻される。
- **Space で鈴**。半径6.2mのキョンシーを1.3〜2.7秒硬直させ、突き飛ばす。
  クールダウン3.4秒。追い詰められたときの逃げ道。
- 焼けている個体は炭化し、遅れて熾火が灯る（発光は burn > 0.15 から立ち上がる）。
  周囲を照らす点光源も持つので、燃えている間だけ回廊が明るくなる。
- **R** で再配置。

新マテリアル3層を手続き生成で追加（官服の綾織り＋団花、屍蝋の肌＋屍斑、
符の紙繊維＋辰砂の呪文）。鳥居と同じベイク経路なので質感の解像度は同じ。

## 境内 — 拡張のための土台

伏見稲荷全体へ広げるための第一歩として、**楼門から本殿までの境内**を作った。
千本鳥居とは別エリアとして作ってあり、後で繋げられる構造にしてある。

### エリア構造（統合のための設計）

```js
WORLD.add({ name:'keidai', contains:(x,z)=> z < 1.0, ground:(x,z)=>({...}) });
WORLD.add({ name:'senbon', contains:()=> true,       ground:(x,z)=>({...}) });
```

エリアは**自分の地面・当たり判定・描画リスト**を持つ。カメラは `WORLD` に
訊き、`WORLD` はプレイヤーが立っているエリアに訊く。**三つ目のエリア
（お塚群、四ツ辻、一ノ峰…）を足すときは、この2行に1行足して地面関数を
書くだけ**で、カメラにも描画にも手を入れなくていい。

当たり判定は AABB のリスト（`WORLD.boxes`、現在44個）。柱・建物・狐像・
灯籠が入っている。

境内は自分の中心線で作ってあり、`KX = 3.02`（参道の入口の x 座標）で
世界座標へずらしている。これで**境内の床と参道の床が段差なく繋がる**。
参道側の散乱物（杉・下草・落葉・地面ストリップ）は `t = -16` から始まって
いて本殿を突き抜けていたので、`CORRIDOR_T0 = 1.0` で切った。

### 建てたもの

実際の配置に沿って、西から東へ登る:

一之鳥居 → 二之鳥居 → 手水舎 → **楼門**（1589年、秀吉寄進）→ **外拝殿**
→ **本殿**（五間社流造）→ 参道へ。段丘で -4.3m から +0.2m まで登る。

### 日本建築のための道具

- **`roofShell()`** — 屋根。平面上の高さは軒からの正規化内挿で決まり、
  **x と z の内挿の `min` を取ると 45° の隅棟が自動的に出る**。1未満の
  指数を掛けると**照り**（凹みの反り）になる。**反り**（軒が隅で跳ね上がる）
  は軒側に加えて棟に向けて減衰させる。この2本の曲線だけで
  「重く見えて隅が飛ぶ」という日本の屋根の性格が出る。
  軒の前後で深さを変えられるので、**流造の非対称な長い前流れがそのまま作れる**。
- **`bracketSet()`** — 斗栱（大斗・肘木・巻斗3・尾垂木）。
  軒下の組物は、建物が「日本建築に見えるか」を決める単一で最大の要素。
- **`rafterRow()`** — 垂木。**`railing()`** — 高欄＋擬宝珠。
- **`buildTamagaki()`** — 玉垣。

マテリアル2層追加: **檜皮葺**（46段の葺き重ね、段ごとの木口の線と影）、
**銅**（窪みに緑青、高い所に金気）。

### 本殿を伏見稲荷らしくする

一般的な流造と伏見稲荷の本殿（1494年、重文）を分けているのは、
主に次の3つ。全部入れた。

- **向拝 + 唐破風** — 前へ張り出した拝所と、その上に載る曲線の破風。
  唐破風の輪郭は「隅から凹んで立ち上がり、中央で凸に反る」S字で、
  **`cos³` がちょうどその変曲を持っている**。両端に少し持ち上げを足すと
  兎毛通の跳ね上がりになる。`karahafu()` はこれ一本。
- **蟇股** — 梁の間に並ぶ carved strut。輪郭だけが遠目に残るので、
  切り抜きではなく天板＋開いた二本足＋金具の塊で組んだ。
- **金具** — 柱の上下の金輪、扉の八双金具、懸魚、千木・鰹木。
  伏見稲荷は「朱と白と金」で出来ている。

あわせて **内拝殿**（鈴緒3本と賽銭箱つき）、**絵馬掛け**、境内の樹木を追加。

### この境内の現状（正直に）

- **楼門・外拝殿・内拝殿・本殿と表参道は見られる状態**。
- **俯瞰にすると世界の縁が見える。** 境内の地面は外へ落として山肌に
  したが、まだ多角形の縁で終わっている。参道側の森と境内の森も
  視覚的に繋がっていない（間に隙間がある）。地上を歩く分には見えない。
- **白壁が暗い**。軒の深い影に入るので空の青い環境光しか当たらず
  青灰色に見える。実際の白壁はもっと明るく浮く。反射光の追加が要る。
- 奥宮、社務所、権殿、神楽殿はまだ無い。
- 千本鳥居の先（奥社奉拝所、熊鷹社、四ツ辻、一ノ峰）はまだ無い。

## 狐人 — キャラクターモデル

伏見稲荷は狐の社なので、獣人は狐にした。**今回はモデルのみ。歩行・走行・
ジャンプは次回**だが、最初から**関節階層の上に載せて作ってある**ので、
アニメーションを足すのは `JOINTS` に角度を書くだけで、ジオメトリを
作り直す必要はない。

### 狙ったバランス

- **7.3頭身。** 8頭身はファッション画、5頭身はデフォルメ。この辺が
  「アニメ寄りだが実在感がある」帯。
- **マズルの突出 85mm。** これより長いと動物、短いと「耳をつけた人間」。
  **獣人デザインが成立するかどうかを決める唯一の数字**だと思う。
- **後肢は指行性**（大腿 → 脛 → 中足 → 肉球）。シルエットだけで
  「獣人」と分からせる要素として、これ以上に効くものは無い。
- **目は解剖学的サイズの約1.25倍**に拡大し、瞼の構造は本物どおり。
  誇張はプロポーションで、作りは写実で。
- **赤狐の柄**（赤褐色の体、喉と腹はクリーム、四肢と耳裏は黒、尾先は白）。
  どの距離でも一目で読める。

### 道具

- **`loft()`** — 楕円リングの連なりを通す有機的なチューブ。フレームを
  平行移動（parallel transport）しているので、長い四肢がねじれない。
  法線はサーフェス上の中心差分から出している。手足・胴・尾・マズル・耳、
  ほぼ全部これ。
- **`ellipsoid()`** — 関節キャップ、頭蓋、眼球。
  関節キャップはチューブより少し大きくしてあるので、肘や膝を曲げても
  継ぎ目が割れない（スキニングが無いエンジンでの必須テクニック）。

マテリアル3層追加: **毛（背）**、**毛（腹）**、**麻布**。
毛は「毛束 → その中の毛 → 先端の淡い差し毛」の3段で、**毛流れが V 方向に
走る**ので、loft のパラメータ化がそのまま四肢に沿って毛を寝かせてくれる。

三角形数は約9,500（左右対称分を含めた実描画は約13,000）。

### 現状（正直に）

立って、地面に接地して、獣人として読める。ただし**もう一周必要**:

- **尾が長すぎて水平に突き出ている**。板に見える。
  分割を減らすか、rest 角度で下に垂らして先を持ち上げるべき。
- **腕が細く、前腕が浮いて見える**。上腕・前腕とも太さを増やし、
  肩の三角筋キャップを大きくする必要がある。
- **胸郭が腰に対して狭い**。シルエットが下重心になっている。
- **頬のラフが目にかぶって、白い当て物のように見える**。
  目が読めていない。顔はもっとも重要な部分なので最優先。
- **上衣が単なる筒**。肩と袖の構造が無い。

`K` キーでモデルの正面に立てる。`F` の俯瞰カメラで自由に回り込める。

## 移動の手触り

元は 1.62m の三脚が 1.55 m/s で幅 1.15m のスロットを動いていた。
背が高く、遅く、閉じ込められて見える。変更:

| | 前 | 後 |
|---|---|---|
| 視点の高さ | 1.62m | **1.46m** |
| 歩き | 1.55 m/s | **4.20 m/s** |
| 走り (Shift) | 3.6 m/s | **9.50 m/s** |
| 横方向の可動域 | ±1.15m | **±2.75m** |

### 視点

- **ホイールで拡大縮小**（画角 14°〜88°）。`-` / `=` でも。
  スナップさせず減衰させている（14°でいきなり切り替わると酔う）。
- **`F` で俯瞰モード** — カメラが体から外れ、当たり判定も重力も無くなる。
  移動は**視線方向**に走るので、下を向いて前進すれば降りる。
  覚える軸が増えないし、全体を見に上がるのがいちばん速い。
  `Space` で上昇、`Shift` で加速。

鳥居の内法は 1.86m、柱は中心 1.085m に立つので、±2.75 にすると
**柱の外側の縁石まで出られる**。そこが低い太陽の光が入ってくる場所なので、
可動域の拡大はそのまま戦術になる。

加えて速度に応じた加減速と歩調に同期したヘッドボブを入れた。

## 次にやること

このプロトタイプで手触りが確認できたら、順に:

1. ~~**影の中判定（CPU側）**~~ — 済（キョンシーの日光判定として実装）。
   パズル用の一般化（任意の点・任意のオブジェクト）はまだ。
2. **WebAudio** — 環境音・足音・鈴・跳躍音。**今いちばん大きな欠落**。
   キョンシーが無音で跳ねてくるのは怖さを半分捨てている。
3. **可動オブジェクト** — 灯籠を押す・回す。動的な影を CSM に入れる。
   「影を作って身を隠す / 光を導いて焼く」の両方に効く。
4. **平面反射** — 水面パズルには SSR では足りない（画面外を反射できない）。
5. **影ハイライト** — アクセシビリティ。影が見えない環境では詰む。任意ではない。

既知の限界:
- 月がない（Act 2）、天候遷移がない（Act 3）、セーブがない、音がない。
- キョンシーの日光判定は鳥居列だけを解析モデル化している。杉の樹冠は
  遮蔽ではなく減衰係数（0.28〜1.0）として掛けているだけなので、
  樹冠の影に立っていても焼ける（遅くはなる）。プレイヤーが推論する対象を
  鳥居に絞るための意図的な単純化だが、正確ではない。
- 跳躍中の当たり判定は円柱近似。押し合いも無いので重なれる。
